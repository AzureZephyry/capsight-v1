# CapSight

CapSight is an in-progress capacity assessment application. The current implementation contains a small Assessment persistence slice. Request Context fields and capacity calculations await validated Knowles requirements.

## Local setup

### Verify a clean checkout without PostgreSQL

Use **Node.js 24.18.0**, pinned in `.nvmrc`, and npm with the committed `package-lock.json`. From the repository root:

`.gitattributes` keeps text checkouts in LF format on Windows and CI so Prettier sees the same content.

```sh
npm ci
npm run verify
```

`verify` generates the ignored Prisma Client, then runs typecheck, ESLint (including architecture boundaries), Prettier check, Vitest, and the production build in order. It exits automatically and stops with nonzero status on the first failure. After dependency installation it requires no PostgreSQL, `DATABASE_URL`, `.env.local`, secrets, external network, or Playwright browser installation. Do not copy another developer's generated files or local environment. `npm run db:generate` is also available independently.

`npm run build` also generates Prisma Client before compiling, including on a fresh hosted checkout or a build with cached dependencies. Generation needs no database connection; install, build, and startup never apply migrations.

Run `npm run dev` and open `http://localhost:3000/assessments` or `/how-capsight-works`. Without database configuration, Workspace shows its safe unavailable state and the product guide remains available. Starting the server does not run migrations or mutate the database automatically.

### Develop persisted Assessments

1. Provide a reachable, dedicated PostgreSQL development database.
2. Copy `.env.example` to ignored `.env.local` and replace the placeholder `DATABASE_URL`. Keep credentials out of source control. Check for an existing process-level `DATABASE_URL`, which takes priority over the file.
3. Generate the client with `npm run db:generate` if not already generated by `verify`.
4. Inspect the configured database's migration state with `npx prisma migrate status`. Pending migrations can produce nonzero status. After confirming the intended development target, apply **already-committed migrations** with `npm run db:migrate:deploy` (`prisma migrate deploy`). This writes schema changes to that target; it is not part of `verify` or CI.
5. Run `npm run dev` and open `http://localhost:3000/assessments`.

The Prisma CLI configuration (`prisma7.config.ts`) reads `DATABASE_URL` from the process environment or `.env.local`; Next.js reads `.env.local` at runtime. Generating the client and validating the schema do not prove connectivity or migration success.

`npm run db:migrate` runs **`prisma migrate dev`**: migration authoring for approved schema changes on a dedicated development database. It is not the default fresh-checkout setup command and may request a reset on drift. Review any such request; do not routinely reset data. There are no automatic reset, db-push, or seed scripts.

## Current behavior

When PostgreSQL is configured and migrated, `/assessments` creates a blank saved Assessment and lists recent saved Assessments. Each Assessment opens at `/assessments/{technical-uuid}`; its section links preserve that ID and reload persisted lifecycle state. A new Assessment begins with Request Context incomplete and unvalidated, so Baseline remains blocked. The revision comparison path is implemented in Application and Infrastructure for a technical concurrency probe. No user-facing edit is available until Knowles validates Request Context fields.

Without a database, the app shows a safe unavailable message. An invalid Assessment ID shows a not-found page. Database or Prisma error details are not shown in the UI.

Missing or invalid `DATABASE_URL` configuration emits a static server-side developer diagnostic. Runtime reads and writes remain lazy; compiling the app does not need database access. Never use a production database for verification scripts.

Light is the default theme. Explicit Light/Dark choices persist as a browser preference across reloads, direct/client navigation, and reopening. Blocked browser storage leaves switching available for the current document. `/how-capsight-works` is available without database access.

## Checks

Run `npm run verify` before pushing or requesting review. Its individual commands remain available: `npm run db:generate`, `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm test`, and `npm run build`. `npm test` runs the colocated Domain/Application Vitest suite once in Node and exits with nonzero status on failure. Test fixtures are synthetic lifecycle state, not Knowles calculation evidence. Run `npm exec prisma validate` for schema validation. Persistence behavior and migration success require separate PostgreSQL verification.

`.github/workflows/ci.yml` runs `npm ci`, Prisma Client generation, typecheck, lint, format check, `npm test`, build, Playwright Chromium headless runtime installation, and `npm run test:e2e` for pushes and pull requests to `main`, using `.nvmrc`. A clean checkout must generate the ignored client before standalone typecheck; `verify` and `build` handle their own generation. Compilation, unit tests, and default browser tests need neither `.env.local` nor a database; CI runs no migrations, database integration tests, or deployment. Use `npm audit` to inspect the locked dependency graph; do not force upgrades automatically. See [the testing strategy](docs/features/capacity-engine-testing-strategy.md) for unit, persistence, future Knowles golden-sample, and browser/E2E verification boundaries.

### Browser / E2E checks

Browser/E2E checks remain separate from `verify`. Install Chromium once (this download needs network access), then use the build produced by `verify`:

```sh
npx playwright install chromium
npm run test:e2e
```

Playwright automatically starts and stops the production application at `http://127.0.0.1:3100`, reusing the completed build. Leave that port free. It explicitly sets `DATABASE_URL` empty for its server, overriding existing process or `.env.local` credentials, and does not reuse other running servers. PostgreSQL and secrets are unnecessary; Workspace shows its existing safe unavailable state. No persistence is mocked or seeded. Rebuild after production source changes; test/config changes alone do not require another build. `npm test` continues to run Vitest only.

The small Chromium suite covers product navigation, the planned closed-loop explanation, theme persistence, branded not-found recovery, keyboard access, and 320px/1440px layouts. Persisted Assessment creation/reopening, workflow navigation, and other database-backed journeys remain a future integration layer. Knowles-dependent calculations remain blocked until validated evidence exists.

For local debugging, run `npm run test:e2e -- --headed`. Failure screenshots/traces are generated in ignored `test-results/`; open a trace with `npx playwright show-trace <path-to-trace.zip>`. CI installs only Chromium's headless runtime and OS dependencies with `npx playwright install --with-deps --only-shell chromium`, reuses its build, and uploads failure artifacts for seven days. Browser binaries stay in Playwright's local cache outside the repository.

Optionally run `node scripts/verify-baseline-workflow.mjs` as a non-mutating TypeScript compiler/Node module-loading smoke check. Its Baseline readiness assertions overlap the durable Vitest suite; it performs no calculation or database access and is retained outside CI.

### Manual PostgreSQL verification

When persistence verification is explicitly needed, run `node scripts/verify-assessment-concurrency.mjs` against a dedicated development database to exercise the actual Application/Infrastructure update path using an existing Assessment. It reads the current revision, advances it once, retries with the stale revision, and checks PostgreSQL for preserved lifecycle state and unchanged other records. Each successful run **mutates the selected record's revision**; it does not create a record and must not run as a routine onboarding/`verify`/CI check. Set `ASSESSMENT_ID` in the process environment to select a particular existing record, or omit it to select the oldest record.

On October 1, 2026, verification against two existing Assessments advanced one record from revision 1 to 2 and rejected the repeated expected revision 1 with `conflict`. Direct PostgreSQL inspection confirmed revision 2, preserved incomplete/unvalidated state, and an unchanged second Assessment. Browser reload/reopen verification was not repeated during this concurrency check.
